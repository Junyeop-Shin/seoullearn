# 서울런 멘토 업무 지원 AI: 프로젝트 요약

자기소개서를 쓸 때 참고하는 요약이다. 2026-10-11 기준이며, 수치는 저장소의 평가 리포트(`docs/rag_results.md`, `eval/reports/`)와 같은 날 다시 돌린 테스트 결과에서 옮겼다. `[본인 확인]`은 저장소만으로는 알 수 없어 지원자가 채워야 하는 곳이다.

## 한 문단 요약

서울런 멘토가 멘토링 외에 되풀이하는 일(규정 찾기, 활동보고서·종합계획서·완료보고서 작성, 멘토 교체 인계)을 줄이는 웹 서비스다. 활동가이드와 공지를 근거로 질문에 답하고(RAG), 저장해 둔 계획서와 회차 기록으로 보고서 칸을 미리 채운다. 멘티가 미성년자라서, 이름은 멘토의 브라우저 밖으로 내보내지 않고 보고서 내용은 서버에 저장하지 않는 구조로 만들었다. 혼자 만든 개인 프로젝트이자 서울시에 제안하려는 시제품이다. 가상 데이터로만 개발하고 평가했고, 실제 멘토가 쓴 적은 아직 없다.

## 배경과 문제

서울런은 서울시의 학습 지원 사업이다. 멘토링에서는 대학생 멘토가 멘티(초·중·고 학생)와 매주 온라인(서로온 화상시스템)이나 오프라인으로 만난다. 한 회기는 16회차(회당 60분)이고, 시간확대(120분)면 8회차다.

- **규정을 찾는다.** 활동가이드는 60쪽이 넘고 공지가 계속 추가된다. 지각 기준, 결석 증빙, 일정 변경 기한을 그때마다 찾아야 하고, 못 찾으면 어디(운영사무국, 자치구 이음단, 학습지원센터)에 물어야 하는지도 헷갈린다.
- **보고서를 쓴다.** 회차마다 활동보고서를 7일 안에 내고, 회기마다 종합계획서를 두 번(1회차 전의 ①, 1회차 뒤의 ②), 완료보고서를 한 번 쓴다. 실제 접속 시간, 증빙 사진, 첨부 파일처럼 빠뜨리면 활동비가 지급되지 않는 항목이 있다.
- **인계가 끊긴다.** 멘토가 바뀌면 다음 멘토는 멘티의 진도와 학습 습관을 처음부터 다시 파악한다.
- **AI를 그냥 붙일 수 없다.** 멘티가 미성년자이고, 보고서에는 출결과 학습 상황에 가정·정서 이야기까지 섞인다.

개발 지침에는 현직 멘토의 경험에서 출발한 프로젝트로 적혀 있다. `[본인 확인: 멘토 활동 기간, 맡은 멘티 수, 이 문제를 직접 겪은 장면]`

## 만든 것

화면은 멘티 한 명이 메뉴 하나다. 멘티를 고르면 사전 연락 → 종합계획서(①, ②) → 회차별 활동보고서 → 완료보고서 순서에서 지금 단계의 화면이 열린다. 멘토는 고르기와 짧은 메모만 하고, 날짜·과목·지난 과제·이번 주 계획은 저장해 둔 자료에서 채워진다. 결과는 플랫폼에 붙여 넣을 글이나 서식 파일로 나온다.

| 기능 | 하는 일 | 방식 |
| --- | --- | --- |
| 매뉴얼 질문 | 활동가이드와 공지에서 답을 찾아 쪽수와 함께 답한다. 답이 없으면 지어내지 않고 문의처와 보낼 글의 초안을 준다 | RAG |
| 사전 연락 | 등록 정보로 멘티(보호자)에게 보낼 문자 문구를 만든다 | 템플릿 |
| 종합계획서① | 플랫폼 입력 칸과 같은 순서로 적는다. 학년·학기·과목의 교육과정 단원을 주차에 나눠 커리큘럼을 채운다 | 규칙과 교육과정 자료. 비워 둔 목표·진단의 초안만 AI(선택) |
| 종합계획서② | 붙여 넣은 강의 목차(또는 캡처 이미지)를 읽어 주차에 나누고, 서식 파일(hwpx, docx)에 채워 내려받는다 | 강의 배분은 규칙, 학습 내용 문장과 이미지 읽기는 AI, 파일 채우기는 브라우저 |
| 활동보고서 | 그 주차 계획, 출결, 인강·과제 수행 여부로 플랫폼 칸을 미리 채운다. 제출 기한과 증빙을 안내하고 인증사진 이름을 바꿔 압축한다 | 규칙 (AI 미사용) |
| 완료보고서 | 화면을 열면 계획서와 회차 기록으로 플랫폼의 네 칸 초안을 쓴다. 기록이 없는 칸은 비운다 | 통계는 규칙, 요약 문장은 AI |
| 인계 요약 | 출석 패턴, 과제 수행, 학습 태도, 수강 진도 네 가지만 뽑아 다음 멘토에게 보낼 글을 만든다 | 허용 목록 + AI |
| 활동비 계산 | 기본수당, 준비수당, 가산금, 결석 유형별 지급을 계산한다 | 규칙 |
| 오프라인 일정·장소, 이음단 연락처 | 매월 이음단에 보내는 일정·장소 문구, 25개 자치구 이음단 채널 바로가기, 장소 지도 | 템플릿 |
| 친화·성장활동, 시간확대 요건 확인 | 신청·결과 내용을 적어 두고 완료보고서 초안의 참고 자료로 쓴다. 증빙사진 압축. 시간확대 요건 네 가지 확인 | 규칙 (AI 미사용) |

설계 원칙은 세 가지다.

1. **AI는 초안까지만.** 멘토가 읽고 고친 뒤 플랫폼에 직접 제출한다.
2. **숫자는 규칙으로, 문장만 AI로.** 회차 배분, 제출 기한, 활동비는 코드가 계산한다. AI가 쓴 문장에 입력에 없는 숫자가 있으면 그 문장을 뺀다.
3. **모르면 모른다고.** 매뉴얼에 없는 내용은 답하지 않고 문의처로 연결한다. 아동 안전 신호가 있으면 AI가 답하지 않고 운영사무국 즉시 보고를 안내한다.

## 구조와 기술

```text
멘토의 브라우저 ── Vue 화면 · 보관함(IndexedDB): 멘티 정보와 초안은 여기에만 저장
      │ /api
frontend (nginx) ─► backend (Spring Boot) ── 로그인·역할, 양식 스키마, 중계(본문 저장 안 함)
                          │                          │
                          ▼                          ▼
                    db (PostgreSQL + pgvector)   ai-server (FastAPI) ──가린 글만──► LLM API
                    회원 · 매뉴얼 색인             가드 → 의도 분류 → RAG / 양식 엔진 / 계산기
```

| 구성요소 | 기술 | 맡는 일 |
| --- | --- | --- |
| frontend | Vue 3, Vite, IndexedDB, nginx | 화면. 멘티 정보와 초안을 브라우저에 보관. 서식 파일 채우기와 사진 압축도 브라우저 안에서 한다 |
| backend | Java 21, Spring Boot 4.1, Spring Security, JPA | 로그인(세션 쿠키, CSRF)과 역할(멘토, 관리자), 로그인 실패 제한, 양식 스키마 제공, AI 서버 중계 |
| ai-server | Python 3.12, FastAPI, LangChain, LangGraph, sentence-transformers | 개인정보 가드, RAG, 의도 분류, 양식 엔진, 활동비 계산 |
| db | PostgreSQL 16, pgvector | 회원 테이블, 매뉴얼·공지 벡터 색인 |
| LLM | OpenAI `gpt-4.1-mini` (LangChain `init_chat_model`이라 설정 두 줄로 제공사 교체) | 문장 생성만 |
| 임베딩 | `dragonkue/multilingual-e5-small-ko-v2` (서버 안에서 실행) | 질문과 문서가 임베딩 때문에 밖으로 나가지 않는다 |

- 실행: Docker Compose(컨테이너 네 개). 저장소 기록으로는 로컬 실행까지다. `[본인 확인: 배포 여부]`
- 규모: 코드 약 1만 4천 줄(Python 6,900, Vue 3,000, JavaScript 2,600, Java 1,500. 테스트 포함), 커밋 41개(2026-10-07 ~ 2026-10-11). `[본인 확인: 기획과 자료 정리를 시작한 때]`
- 자동 테스트: AI 서버 143개, 화면 86개, 백엔드 22개(2026-10-11 실행, 모두 통과). API 키 없이 돈다(가짜 LLM). 여기에 화면을 끝까지 눌러 보는 브라우저 점검 스크립트(Playwright)와 서버 유출 검사 스크립트가 있다.

## AI와 RAG를 쓰는 방식

### 매뉴얼 질문 (RAG)

1. **문서:** 원본 PDF를 그대로 자르지 않고, 활동가이드를 섹션 단위 문서 18개로 다시 정리했다(표는 행 하나가 사실 하나가 되게). 공지 12개를 더해 30문서, 134청크다. 문서마다 쪽수, 게시일, 활동가이드의 어느 내용을 바꾼 공지인지를 머리말에 적는다.
2. **검색:** 벡터 검색(pgvector)과 BM25를 순위로 합친 하이브리드(RRF)다. 용어집 56개로 멘토 말투를 공식 용어로 보강한다(주간보고서 → 활동보고서, 못 왔 → 결석). 상위 5개 청크를 쓴다.
3. **답변:** LLM에는 개인정보를 가린 질문과 5개 청크만 보낸다. 출력은 JSON(답할 수 있는지 yes·partial·no, 답, 인용 번호, 문의처)이고 형식이 틀리면 오류로 기록한다.
4. **답을 다 못 했을 때:** 문의처와 보낼 글의 초안을 준다. 연락처는 LLM이 아니라 코드가 붙인다.
5. **아동 안전 신호:** 검색도 LLM 호출도 하지 않고 운영사무국 즉시 보고 안내를 돌려준다.

### 의도 분류

LangGraph 그래프(가드 → 분류 → 안전 안내·매뉴얼 질문·화면 안내·활동비 계산기)다. 규칙(키워드)으로 먼저 나누고 애매할 때만 LLM에 묻는다. 가상 문장 30개에서 규칙만으로 83.3%, 규칙과 LLM을 함께 쓰면 100%였고 LLM은 5문항에만 불렸다. 평가셋과 규칙을 같은 사람이 같은 날 만들어 실제보다 높게 나왔을 수 있다.

### 양식 엔진

양식 하나가 JSON 파일 하나다. 칸마다 누가 채우는지(멘토 입력, 자리표시, 규칙 계산, AI 초안)를 스키마에 적어 두고 엔진이 그대로 따른다. LLM에 보내기 전에 가드로 개인정보를 가리고 정서·가정·건강 문장을 문장 단위로 뺀다. LLM 출력에 입력에 없는 숫자가 있으면 그 문장을 빼고 경고한다.

### AI를 쓰지 않는 곳

회차·날짜 계산, 제출 기한, 활동비, 단계 전이, 사전 연락과 이음단 문구, 교육과정 단원 채우기, 강의 배분, 활동보고서 칸 채우기, 서식 파일 채우기, 사진 압축은 모두 규칙이나 템플릿이다.

### 기술 수준

- 검색과 생성의 구성은 널리 쓰이는 방식이다: 하이브리드 검색과 RRF, 규칙 기반 질의 보강, JSON 구조화 출력, 규칙을 먼저 쓰는 라우팅.
- 쓰지 않은 것: 파인튜닝, 에이전트형 다단계 검색, LLM으로 질문 다시 쓰기. 리랭커(cross-encoder)는 실험했지만 넣지 않았다(아래 '리랭커를 넣지 않았다').
- 내세울 점은 기법의 새로움이 아니라 (1) 평가셋을 먼저 만들고 개선을 하나씩 재며 정한 과정, (2) 개인정보를 약속이 아니라 구조로 막은 설계, (3) AI를 쓸 곳과 쓰지 않을 곳을 가른 판단이다.

## 개인정보 설계

| 원칙 | 구현 |
| --- | --- |
| 이름은 브라우저 밖으로 나가지 않는다 | 멘티 이름·학년, 멘토 이름·연락처·소속은 멘토 브라우저에만 저장한다. 서버가 만든 초안에는 `[멘티명]` 자리표시가 오고 화면이 그 자리를 채운다. 멘티 연락처와 학교는 적는 칸이 없다 |
| 저장하지 않는다 | 질문과 보고서 내용은 서버의 DB·로그·캐시에 남기지 않는다. 로그에는 길이와 결과 유형만 남는다 |
| 가려서 보낸다 | LLM에 보내기 전에 가드가 이름, 전화번호, 이메일, 학교명을 가린다. 정서·가정·건강 이야기는 초안의 재료로 쓰지 않는다 |
| 넘길 것만 넘긴다 | 인계 요약은 허용 목록 방식이다. 허용한 네 항목의 출처 칸만 LLM에 보내고, 학업 수준과 상담 내용은 보내지도 않는다 |
| 확인한다 | 유출 검사 스크립트가 가짜 개인정보가 든 가상 기록으로 서비스를 호출한 뒤 컨테이너 로그, DB 전체, 캐시에 조각이 남았는지 찾는다. 브라우저 점검 스크립트는 화면이 서버로 보낸 모든 요청에 이름과 연락처가 없는지 확인한다 |

남는 위험: 가드와 민감 내용 필터는 정규식과 낱말 목록이라 목록에 없는 표현은 지나간다. 가린 글이라도 LLM 제공사로 전달된다. 브라우저 보관함은 암호화하지 않는다.

## 평가와 결과

평가셋은 멘토가 물을 법한 질문 72개다(답이 없는 질문 8개, 일부만 답할 수 있는 질문 12개 포함). 문항마다 정답, 정답 근거(문서와 쪽), 문의처가 있다. 지원자가 직접 만든 가상 질문이다. 아래는 2026-10-08에 잰 값이다.

### 검색 (활동가이드만, 근거가 있는 68문항)

| 단계 | hit@1 | hit@5 | MRR |
| --- | --- | --- | --- |
| 기본형: 원본 PDF를 500자씩 자르고 벡터 검색 | 44.1 | 82.4 | 0.595 |
| 활동가이드를 섹션 단위 문서로 다시 정리 | 57.4 | 83.8 | 0.683 |
| 벡터 + BM25 하이브리드 | 54.4 | 88.2 | 0.682 |
| 용어집 질의 보강 (최종) | 58.8 | 91.2 | 0.722 |

hit@5는 정답 근거가 검색 결과 상위 5개 안에 있는 문항의 비율이다.

| --- | --- | --- | --- | --- |
| 답할 수 있는지 판단 | 73.6% | 80.6% | 83.3% | 80.6~81.9% |
| 지어내기 (답이 없는데 답함) | 8개 중 1개 | 8개 중 1개 | 4개 중 1개 | 같음 |
| 과잉 거절 (답이 있는데 거절) | 3.8% | 0% | 3.3% | 1.9~3.8% |
| 문의처 | 73.6% | 86.1% | 86.1% | 76.4~80.6% |
| 아동 안전 질문의 즉시 연결 | 100% | 100% | 100% | 100% |

첫 측정은 하이브리드와 용어집까지 적용한 상태에서 한 번 잰 값이다. '최종' 두 열이 실제 서비스와 같은 조건이고, 마지막 열은 검색된 자료 5개의 순서만 섞어 두 번 더 잰 값이다.

### 그 밖

- **임베딩 모델 세 개 비교:** 경량 모델(1.2억 파라미터)과 대형 모델 두 개(`BAAI/bge-m3`, `multilingual-e5-large-instruct`)를 쟀다. 대형 모델은 색인이 약 20배 느리고 메모리를 2~3배 쓰는데 hit@5 차이는 5%p 미만이라 경량 모델을 유지했다.
- **보고서 초안(가상 사례 14건):** 필수 항목 채움률 100%, 입력에 없는 숫자·날짜 0건, 개인정보·민감 내용 노출 0건. 활동보고서 초안을 AI가 쓰던 초기 설계에서 잰 값이다. 지금 활동보고서 화면은 AI를 쓰지 않는다.

### 이 수치를 쓸 때 알아야 할 것

- 평가셋, 보고서 사례, 거르는 규칙을 모두 한 사람이 만들었다. 실제 멘토의 질문에서는 달라질 수 있다.
- 답변 지표는 5문항(약 7%p) 안의 차이를 구별하지 못한다. 문의처 86.1%는 검색 순서 그대로일 때의 값이고 순서를 섞으면 76.4~80.6%다.
- 지어내기는 줄이지 못했다. 프롬프트로 고치려 했으나 효과가 확인되지 않아 되돌렸다.
- 2026-10-08 뒤에 가드 규칙을 더 고치고 공지 1개를 추가했는데, 그 뒤로는 다시 재지 않았다.
- `docs/rag_results.md`와 `docs/proposal.md`에는 기본형 hit@5가 80.9로 적혀 있다. 가드를 고치기 전에 잰 값이고, 같은 조건으로 다시 잰 값이 위 표의 82.4다. 한 글 안에서는 한쪽만 쓴다.

## 문제를 푼 과정 (자기소개서 소재)

### 평가와 AI

1. **모델보다 문서 구조가 먼저였다.** 원본 PDF를 500자씩 자른 기본형에서 활동가이드를 섹션 단위로 다시 정리하니 1위 적중률이 44.1%에서 57.4%로 올랐다. 1위 적중률로는 전체 개선 단계 가운데 가장 큰 폭이다.
2. **기준을 먼저 정하고 임베딩 모델을 골랐다.** "경량 모델과 최고 모델의 hit@5 차이가 5%p 미만이면 경량 모델"이라는 기준을 두고 세 모델을 쟀다. 대형 모델은 BM25와 합치면 오히려 내려갔다. 대형 모델이 1위 적중률에서는 13.2%p 앞선다는 점도 기록에 남겼다.
3. **개인정보 가드가 검색을 망치고 있었다.** 줄인 학교명을 가리는 규칙이 '바꾸고', '한다고' 같은 말을 학교명으로 가려 72문항 중 7문항의 질문이 손상돼 있었다. 고치자 답할 수 있는지 판단이 73.6%에서 79.2%로 올랐다. 보호 장치도 측정 대상이라는 것을 배웠다.
4. **리랭커를 넣지 않았다.** 리랭커는 1위 적중률을 58.8%에서 77.9%로 올렸지만 답변 지표는 오르지 않았고 CPU에서 질문당 10초쯤 걸렸다. 왜 그런지 보려고 같은 자료 5개의 순서만 뒤집는 대조 실험을 했더니 리랭커를 붙였을 때와 같은 크기로 지표가 움직였다. 모델이 상위 5개를 모두 읽으므로 순서는 답을 거의 바꾸지 않는다는 결론을 냈다.
5. **측정 오차를 재고, 그 안의 차이는 개선으로 치지 않았다.** 자료 순서만 바꿔도 문의처 정확도가 86.1%에서 79.2%로 움직였다. 그래서 최종 평가는 순서를 섞어 세 번 쟀다. LLM 채점은 맞는 답을 0점 처리하는 경우가 확인돼 결과 표에서 빼고 규칙으로 계산한 지표만 실었다.
6. **평가셋에 맞춰 고치는 것을 피했다.** 용어집은 홀수 번호 문항만 보고 고치고 짝수 번호로 확인했다(짝수 문항 hit@5 88.6% → 91.4%). 답변 규칙은 세 번 고쳐 재고 효과가 확인된 두 가지만 남겼다.

### 개인정보

1. **이름 없이 자동 입력을 했다.** 서버와 LLM에는 `[멘티명]` 같은 자리표시만 오가고 화면이 그 자리를 채운다. 이름을 서버에 두지 않으면서 보고서의 이름 칸을 채우기 위한 구조다.
2. **유출 검사가 실제 문제를 잡았다.** 평가용 LLM 응답 캐시가 API 서버에서도 켜져 있어 답변이 디스크에 쌓이고 있었다. 검사 스크립트가 찾아내 고쳤다.
3. **코드 검토에서 누출 경로를 찾았다.** 플랫폼에서 복사해 붙여 넣는 활동보고서에는 이름 칸이 들어 있는데 서버에서 회차별로 나누고 있었다. 나누는 일을 브라우저로 옮기고 서버 API를 없앴다. 화면 주소에 멘티 이름이 들어가 Referer로 나갈 수 있던 것도 출처만 싣게 고쳤다.
4. **금지 목록 대신 허용 목록을 썼다.** 인계 요약은 무엇을 빼라고 하지 않고, 허용한 네 항목의 출처 칸만 LLM에 보낸다.

### 제품 판단

1. **AI를 덜 쓰는 쪽으로 고쳤다.** 처음에는 활동보고서 초안과 표현 다듬기를 AI가 했다. 메모체로 쓰는 글이라 얻는 것이 작고 뜻이 바뀔 위험이 있어 없앴다(2026-10-11). 지금 활동보고서 화면은 규칙만 쓴다.
2. **화면을 실제 업무 순서에 맞췄다.** 단계를 7개에서 4개로 줄이고, 화면의 칸을 플랫폼 입력 칸과 같은 구성·순서로 바꿨다. 완료보고서는 묻는 칸을 없애고 화면을 열면 초안이 써져 있게 했다.
3. **없는 내용은 만들지 않게 했다.** 완료보고서는 기록이 없는 칸을 비우고 LLM을 부르지 않는다. 결석 회차에는 학습 내용 칸이 없다. 감성케어 상담 칸은 초안을 만들지 않는다.

## 한계와 아직 하지 않은 것

- 실제 멘토가 쓴 적이 없다. 수치는 모두 가상 데이터로 잰 것이다.
- 작성 시간이 얼마나 줄었는지는 재지 않았다. 기록표(`docs/time_measurement.md`)만 있고 비어 있다. 동료 멘토 설문도 하지 않았다.
- 서울시 제안은 초안(`docs/proposal.md`) 단계다. `[본인 확인: 제출 여부와 일정]`
- 지어내기(자료에 일부만 있는 내용을 다 답한 것처럼 말하는 문제)를 줄이지 못했다.
- 보호 장치는 규칙이라 목록에 없는 표현은 지나간다. 지어내기 검사는 숫자만 본다.
- 협약 장소는 임시 자료다(카카오맵에서 찾은 스터디카페 150곳. 실제 협약 장소가 아니다). 플랫폼 입력 칸의 글자 수 제한처럼 실제와 맞춰 보지 못한 부분이 있다.
- 공지가 새로 나오면 사람이 문서 규칙에 맞춰 넣어야 한다.

## 만든 방식과 본인 역할

- 1인 프로젝트다. 단계별 개발 지침(`docs/BUILD_GUIDE.md`, 600줄)에 작업 단위와 완료 기준(관문)을 적어 두고 그 순서로 진행했다. 개선은 한 번에 하나씩 적용하고 같은 평가셋으로 다시 잰다는 규칙을 두었다.
- 구현은 AI 코딩 도구(Claude Code)와 함께 했다. 지원자는 요구사항을 정하고, 만들어진 화면을 직접 써 보며 방향을 고쳤다.
- 지원자가 내린 결정으로 기록(`docs/workflow.md`)에 남은 것: 단계를 7개에서 4개로 줄임, 오프라인 일정·장소를 화면 하나로 합침, AI 표현 다듬기 삭제, 완료보고서를 플랫폼의 실제 입력 칸 네 개로 다시 구성, 내 준 과제는 지난 보고서의 `과제:` 줄에서만 불러오기, 인증사진 이름 규칙, 인계 글은 이 서비스로 만든 것만 처리, 교육과정 자료 정리.
- `[본인 확인: 코드에서 직접 쓰거나 고친 부분, 평가셋 72문항과 활동가이드 정리본을 만든 방식, 들인 기간]`
- 구현 범위를 말하는 표현('직접 구현', '설계', 'AI 도구 활용')은 지원자에게 확인하고 쓴다.

## 다음에 할 만한 일

계획이지 한 일이 아니다.

- 실제 멘토 질문으로 평가셋을 넓히고, 같은 설정을 여러 번 재 평균을 쓴다.
- 일부만 답할 수 있는 질문을 다 답한 것처럼 말하는 문제를 고친다(프롬프트로는 고치지 못했다).
- 공지가 활동가이드를 바꾼 주제에서 공지를 먼저 찾게 한다.
- 작성 시간을 전후로 재고, 동료 멘토에게 써 보게 한다.
- 실제 서식과 플랫폼 입력 칸, 협약 장소 목록을 받아 맞춘다.
